# ADR-0006: Navmesh and pathfinding — a pure-TypeScript bake and query in the sim

- **Status:** Proposed
- **Date:** 2026-10-02
- **Decider:** Owner
- **Bead:** `mw-e11.4`

## Decision

Creature navigation uses a **pure-TypeScript, Recast-style bake and query that live in `src/sim/nav`**,
with no navigation library. The bake runs at content build time (`pnpm nav:bake`). It turns a scene's
grey-box geometry into `src/content/data/navmesh/<scene>.json`, a schema-validated content type that is
committed, and `pnpm nav:check` and a unit test fail when the file is stale. The mesh is made of
axis-aligned rectangles with a planar height, the portals between them, off-mesh links (jump, drop and
climb) and doorway polygons tagged with their door. Queries are A* over polygons with per-creature
capability masks (content's `NavAgent`), live door states and string pulling. They run through a request
queue whose per-tick budget is counted in deterministic work units. AI's `move-to` and `follow-route` use
the queue through `navmeshNavigation`, which implements the existing `AiNavigation` port.
[recast-navigation-js](https://github.com/isaac-mason/recast-navigation-js) (Recast/Detour compiled to
WASM) is rejected for now. It is faster, but it would bring a second implementation to keep in step with
the pure-TS fake the sim needs anyway, an async WASM load injected from `src/game`, and about 0.9 MB of
assets, all for geometry the pure-TS bake handles exactly. The triggers for reopening the decision are
listed at the end.

## Context

- **The bead (`mw-e11.4`):** the navmesh is baked from grey-box geometry at content build time and stored
  as data. Paths are found in the sim, deterministically, with capability masks (`mw-e12.6`), doors that
  close and lock (`mw-e03.18`), off-mesh links, smoothing, a per-tick request queue and simple avoidance.
  *"If a WASM library is used, the query layer must still be deterministic and wrapped behind a sim
  interface with a pure-TS fake for unit tests."* AC-5 sets a 0.5 ms per-tick budget, and AC-6 requires
  the testbed bake in ≤ 10 s.
- **Contract §2 and §3:** rules live in `src/sim`. They use no wall clock and no `Math.random`, route
  transcendentals through `simMath`, and have 100 % coverage. Replays must hash identically. The sim may
  import content only as types and may not load WASM (lint rule: the game injects Rapier into the
  physics port, ADR-0001).
- **What the geometry is:** grey-box scenes are kit pieces of boxes and wedges, placed on a grid and
  turned only in quarter turns (`src/sim/scene/layout.ts`). Every solid is an axis-aligned box or a ramp
  along an axis, and doors are spawns with a known closed-leaf box (`src/sim/mechanisms/geometry.ts`).
- **What already existed:** `AiNavigation` (`src/sim/ai/navigation.ts`), a straight-line placeholder
  that says "a navmesh-backed port replaces it without touching behaviours". Content's locomotion model
  (`NAV_BITS`, `NAV_AREAS`, `NAV_LINK_KINDS`, `canTraverseLink`) already defines the capability masks
  the bake stores and queries test.

## Options considered

| Option | Summary | Result |
|---|---|---|
| **Pure-TS bake + query in `src/sim/nav`** | Voxelise boxes and wedges into a cell grid, erode by the agent radius, merge into rectangles, link gaps and climbable faces; A* plus funnel at run time | **Chosen** |
| recast-navigation-js 0.43.1 (Recast/Detour in WASM) | Bake triangle soup with Recast; query with Detour behind a sim interface, with a pure-TS fake for tests | **Rejected for now**: needs the pure-TS fake anyway (so two implementations), an async WASM load injected from `src/game`, and +339 KB WASM plus 560 KB JS glue. Jump, drop and climb links would still be generated by our own code. Its speed is not needed at grey-box scale (see Evidence) |
| A uniform grid with A* over cells (no navmesh) | Pathfind on the eroded cell grid directly | **Rejected**: about 40 k nodes for the testbed instead of about 170 polygons, so the search costs several times the budget, and the zig-zag paths need smoothing anyway |
| Hand-authored waypoint graphs | Designers place nodes and edges per scene | **Rejected**: the bead asks for a baked navmesh, and authored graphs drift from the geometry |

## Evidence

Machine: the contract reference machine, MacBook Pro M1 Pro, 16 GB, macOS 27.0.1, Node 24.21.0. It was
shared with other agent sessions (load average 7–9).

### The pure-TS bake on the testbed (AC-6)

`pnpm nav:bake testbed` loads and validates all content, lays out the scene, bakes and writes the file:

| | Value |
|---|---|
| Bake alone (`bakeNavMesh`, cell 0.125 m, humanoid agent r 0.35 m, h 1.8 m, step 0.4 m) | 110–200 ms |
| Whole command incl. Vite start-up and content load | ~1.3 s wall |
| Output | 169 polygons, 239 portals, 143 off-mesh links (jump, drop, climb), 1 door |
| File | 22 KB of JSON, one row per line |

`tests/integration/navmesh.test.ts` (AC-6) runs the bake into a scratch copy of the content in about
0.15 s. The result passes the full content validation and equals the committed file.
`src/tools/navmesh/cli.test.ts` fails when the committed file is stale.

### Query cost and the per-tick budget (AC-5)

The budget is counted in work units: one per polygon expanded, 8 for setting up a search (snapping the
start and goal), and one per path polygon for string pulling. `NAV_UNITS_PER_MS = 800` converts
milliseconds to units. `tests/bench/nav-queue.bench.ts` submits 30 requests across the testbed (room,
corridor, arena, closet, ledge; humanoid and goblin profiles) in one tick, with a 0.5 ms budget (400
units per tick):

| | Value |
|---|---|
| Measured cost per unit (under Vitest) | ~0.5 µs |
| Typical request (room → arena) | 60–80 µs, 40–170 units |
| Ticks to finish all 30 | 7–8 (AC-5: ≤ 10); the first tick always defers some |
| Time of a tick that spends its whole budget | median 0.20 ms, p95 0.26 ms (AC-5: ≤ 0.5 ms) |

The margin (about 2.4× on the reference machine) covers slower CI runners. The bench asserts the median,
as the other perf benches do.

### recast-navigation-js 0.43.1 on the same geometry

The testbed's solids were exported as triangle boxes (wedges with their low edge lowered) and baked with
`generateSoloNavMesh` (cs 0.125, ch 0.05, walkable radius 3 cells, height 36, climb 8, 45°). The script
ran in a scratch directory and is not committed:

| | recast-navigation | Pure TS |
|---|---|---|
| Licence / `npm audit` | MIT / 0 vulnerabilities | n/a (no dependency) |
| Assets | 339 KB WASM (131 KB gzip) + 560 KB JS glue (or a 1 MB asm.js build) | none (the code is tree-shaken until wired) |
| Init | async, ~20 ms | none |
| Bake (testbed) | 7–20 ms | 110–200 ms |
| Polygons | 122 | 169 |
| `computePath` room → arena | ~9 µs | ~40–60 µs (whole search incl. snapping) |
| Repeat query identical | yes | yes (bit for bit, tested) |
| Jump / drop / climb links | authored off-mesh connections only | generated by the bake |
| Door gating, capability masks | poly flags + query filter (16 flag bits) | door polygons + `NavAgent` masks and limits |

Detour is faster, by about 5× per query. Both easily meet the bead's budgets at grey-box scale. Neither
bake comes near the 10 s limit.

Not tested: Recast on non-grey-box meshes; either option on a level the size of Briar Glen or Wendmouth
(thousands of polygons); browser (V8 in Chrome) timings. Node uses the same V8.

## Consequences

- **New code.** `src/sim/nav` contains the bake, the stored format, `NavMesh`, A* with funnel
  (`NavPathSearch`, `NavMeshQuery` implementing `NavQuery`), the queue, doors (`worldNavDoors` reads the
  mechanisms' live state), separation steering and `navmeshNavigation`. `src/tools/navmesh` with
  `pnpm nav:bake` and `pnpm nav:check` is the content-build side. Content type `navmesh` has the
  `checkNavmeshes` load check.
- **Capabilities.** The sim restates content's capability bits and link rules (it may not import content
  values). `tests/integration/navmesh.test.ts` proves they agree with `canTraverseLink` and
  `canEnterArea` for every locomotion profile.
- **One agent size per navmesh.** Scenes are baked for the humanoid radius (0.35 m). Smaller creatures
  path conservatively. Bigger ones (Briar Wolf 0.4 m, Brother Horn) may clip corners until there is one
  navmesh per agent size class (follow-up bead).
- **Saves.** Routes live in the `nav.route` component and are saved. The queue's in-progress search is
  not: a save taken while a request waits resubmits it on load.
- **Re-bake.** Any change to a scene, a kit piece or a material's climb grade means running
  `pnpm nav:bake`, and the check fails until it is done. Bake settings stay in each file, so a scene can
  be re-baked with its own settings.
- **Swappable.** AI code depends on `AiNavigation`, and queries depend on `NavQuery`. A Detour-backed
  implementation could replace the search behind the queue with this one as its pure-TS fake, if the
  triggers below fire.

## Revisit triggers

- A level contains solids that are not axis-aligned boxes or quarter-turn wedges (rotated pieces,
  imported meshes): the pure-TS bake cannot rasterise them.
- On the reference machine, `pnpm nav:bake` takes more than 5 s for any scene, or a navmesh exceeds 2,000
  polygons.
- The nav queue bench (or `mw-e11.18`'s stress scene) shows a request p95 above 0.5 ms, or more than 10
  ticks to answer 30 requests, at the shipped budget.
- Crowds or 3D flight come into scope (both out of scope for this bead).
